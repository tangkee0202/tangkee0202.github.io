我的系统目前包含两个 ROS 2 工作空间：

- [rslidar_slam_tk](https://gitee.com/tang_kee/rslidar_slam_tk)
- [nav2_tk](https://gitee.com/tang_kee/nav2_tk)

这两个工作空间不应该在论文中被写成两个互不相关的项目。更合适的思路，是把它们看成同一项巡检任务的前后两个阶段：

- **rslidar_slam_tk** 解决机器人第一次进入未知环境时，怎样完成建图、自主探索和多车地图融合；
- **nav2_tk** 解决地图建立以后，怎样完成定位、路径规划、多车调度和重复巡检。

把这两个阶段串起来，论文的主线就可以概括为：

> 基于 5G LAN 和边缘计算，研究多台移动机器人在桥梁内部未知环境中的协同建图与自主探索，并在建成地图上完成自主导航和重复巡检。

## 两个工作空间怎样组成一条技术路线

整套系统可以按照“先认识环境，再执行巡检”来理解。

```text
第一阶段：未知环境

车端 RSLidar、IMU、轮式里程计
              │
              ▼
     5G LAN 传输传感器数据
              │
              ▼
边缘侧 SLAM Toolbox + Nav2 + explore_lite
              │
              ├── 单车自主探索
              ├── 多车独立建图
              └── 多机器人地图融合
              │
              ▼
         生成统一环境地图


第二阶段：已有地图

统一地图 + 融合里程计 + RSLidar
              │
              ▼
       Map Server + AMCL
              │
              ▼
      Nav2 规划、避障与控制
              │
              ├── 单点和多点导航
              ├── 多机器人任务下发
              ├── 连续往返巡航
              └── 固定路线重复巡检
```

这样组织后，两个工作空间之间的关系不再是“一个负责 SLAM，一个负责 Nav2”这么简单，而是形成了一个完整的任务闭环：

```text
自主探索 → 建立地图 → 融合地图 → 地图定位 → 路径规划 → 重复巡检
```

## rslidar_slam_tk 在论文中承担什么

**rslidar_slam_tk** 对应论文中的“未知环境建图与探索阶段”。

车端运行底盘、RSLidar、IMU 与里程计融合等基础节点，并向边缘主机提供：

- 每台车的 LaserScan；
- 融合里程计 odometry/filtered；
- odom → base_link 的动态 TF；
- base_link → rslidar 的静态 TF；
- 底盘速度控制接口。

边缘侧使用 SLAM Toolbox 建立每台车自己的地图。Nav2 直接使用实时地图、激光扫描和融合里程计进行路径规划与避障，explore_lite 则根据地图中的未知区域生成前沿目标。

这个工作空间已经包含几项与实车自主探索直接相关的改进：

- 使用最新可用 TF，减少网络与计算延迟导致的 TF 外推错误；
- 启动探索前进行低速小圆运动，主动积累初始地图；
- 将前沿目标从未知区域中的质心调整到附近可达的自由栅格；
- 调整 SLAM 节点生成密度、回环范围和障碍物写入条件；
- 将每台车的地图、雷达和 TF 限制在各自命名空间中；
- 使用 map_merge 将多台机器人的地图合并为 merge/map。

这部分可以为论文提供三类内容：

1. 单机器人自主探索的基础方法；
2. 桥梁狭长、重复结构环境中的 SLAM 与前沿选择问题；
3. 多机器人地图融合与协同探索的基础。

## nav2_tk 在论文中承担什么

**nav2_tk** 对应论文中的“已有地图导航与重复巡检阶段”。

地图建立并保存后，边缘主机通过 Map Server 发布共享地图，每台机器人分别运行 AMCL 和 Nav2。当前系统已经包含：

- AMCL 地图定位；
- NavFn 全局规划；
- DWB 局部控制；
- 全局和局部代价地图；
- 路径与速度平滑；
- 行为树导航和恢复行为；
- NavigateToPose、NavigateThroughPoses 和 FollowWaypoints；
- 多机器人目标路由与任务取消；
- 三车领航—跟随目标接口；
- 多航点连续往返巡航；
- Qt/RViz 多机器人操作界面；
- 手动控制与 Nav2 速度仲裁。

这个工作空间在论文中的主要作用，不是证明“我会使用 Nav2”，而是为建图完成后的巡检任务提供执行平台。

尤其是连续往返巡航，可以直接对应桥梁的周期性巡检。机器人在地图上记录 A、B、C、D 等巡检点后，可以持续执行：

```text
A → B → C → D → C → B → A → …
```

以后如果加入相机或病害检测模块，就可以在固定构件附近重复采集数据，并比较不同巡检周期的变化。

## 两个工作空间真正的连接点

论文中不能只说“先运行一个工作空间，再运行另一个工作空间”，还需要明确它们交换的核心信息。

### 地图

未知环境阶段由 SLAM Toolbox 生成每台车自己的地图，再由 map_merge 生成融合地图。融合后的结果经过检查和保存，可以成为已有地图导航阶段的 Map Server 输入。

需要注意，目前 merge/map 主要用于融合显示和归档，还没有直接接入另一套 Nav2 作为共享导航地图。因此，从实时融合地图到稳定巡检地图之间，还需要增加地图质量检查、保存、坐标统一和模式切换流程。

### 位姿与坐标系

两个工作空间都使用同一套基本坐标关系：

```text
map → tracerN/odom → tracerN/base_link → tracerN/rslidar
```

实时建图阶段的 map → odom 由 SLAM Toolbox 提供；已有地图阶段则由 AMCL 提供。odom → base_link 始终来自车端融合里程计。

只要地图坐标、机器人命名空间和传感器外参保持一致，两个阶段就可以使用同一批机器人和传感器数据。

### 任务

探索阶段的任务是尽快覆盖未知区域，输出完整地图；巡检阶段的任务是在已有地图中稳定到达指定构件，并按照固定路线重复运行。

因此，两个工作空间不是在重复完成同一件事，而是在完成巡检系统生命周期中的不同任务。

## 论文真正需要解决的问题

现有代码已经能够让单台机器人自主探索，也能够让多台机器人分别运行 SLAM 并融合地图。但“多台机器人同时运行”并不等于“多机器人协同”。

目前每台车仍然独立选择前沿。不同机器人可能前往同一片区域，产生重复探索；在狭窄通道中还可能相互等待、反复重规划或堵住对方。

所以，我认为论文最值得研究的问题是：

> 如何在 5G LAN 和边缘计算架构下，利用融合地图统一分配多机器人的探索与巡检任务，减少重复覆盖和路径冲突，并在建图完成后平滑切换到固定路线自主巡检？

围绕这个问题，可以设计一套边缘侧的协同任务模块：

1. 从融合地图中提取全局前沿；
2. 获取每台机器人的位置、运行状态和 Nav2 路径代价；
3. 根据前沿信息增益、路径长度和机器人负载计算任务收益；
4. 为不同机器人分配不同的探索目标；
5. 当前沿消失、机器人离线或导航失败时重新分配；
6. 对狭窄通道设置占用、优先级或错峰规则；
7. 地图完成后保存融合地图，并切换到 AMCL 与固定巡检路线。

这部分才是把两个现有工作空间真正融合成论文方法的关键。

## 哪些内容可以写进论文

论文内容可以分为“核心研究”“系统方法”和“实验平台”三个层次。

### 可以作为核心研究的内容

| 内容                                | 适合放在论文哪里 | 是否可能成为创新点           |
| ----------------------------------- | ---------------- | ---------------------------- |
| 基于融合地图的多机器人前沿分配      | 方法章节         | 可以，适合作为主要创新       |
| 狭窄通道中的任务冲突与优先级处理    | 方法章节         | 可以                         |
| 机器人离线、目标失效后的动态重分配  | 方法章节         | 可以                         |
| 从协同建图切换到重复巡检的任务流程  | 方法或系统章节   | 可以作为系统创新             |
| 5G 时延、边缘负载与任务分配联合考虑 | 方法章节         | 如果形成模型和算法，可以     |
| 桥梁重复结构中的地图融合约束        | 方法章节         | 如果改进融合算法并验证，可以 |

其中，最适合作为主创新的是“基于融合地图的多机器人任务分配”。它正好连接 rslidar_slam_tk 的地图与探索功能，以及 nav2_tk 的多车导航和任务执行功能。

这些内容对完整系统是必要的，但大部分采用了已有开源算法。论文中应说明怎样使用、为什么适合当前场景，以及为实车做了哪些调整，而不能仅凭“系统里用了 Nav2”就把它写成创新点。

## 哪些主要是工程实现

下面这些内容对项目运行很重要，但没有必要在论文正文中大篇幅展开：

- SSH 密钥配置和各机器人 IP 地址；
- ROS_DOMAIN_ID、环境变量和终端启动顺序；
- colcon 构建命令与软件依赖安装；
- Launch 文件的具体组织方式；
- 单实例文件锁和分阶段加载组件；
- 日志目录、PID 文件和进程清理脚本；
- Qt 界面的按钮、页面切换和日志窗口；
- RViz 显示项的动态裁剪；
- 地图文件名称和路径；
- 每个话题的完整发布订阅清单；
- 具体命令行输入格式。

论文中最多用一小节概括系统可靠性设计，例如“启动前检查传感器和 TF”“使用速度仲裁避免多源控制冲突”“通信异常时执行安全停车”。详细代码实现可以放进附录、项目文档或开源仓库，不需要占据方法章节。

## 哪些不能直接写成创新点

为了让论文的贡献更清楚，有几类工作需要特别注意：

- 使用 SLAM Toolbox 本身不是创新；
- 使用 AMCL、NavFn、DWB 或 Nav2 本身不是创新；
- 调整速度、膨胀半径和匹配阈值通常只是参数整定；
- 接入 explore_lite 或 map_merge 本身不是创新；
- 开发 Qt/RViz 控制界面主要属于工程实现；
- 使用 5G LAN 本身也不等于通信创新。

如果希望 5G LAN 和边缘计算成为论文贡献，就需要进一步建立计算卸载、通信代价或任务分配模型，并通过不同网络条件下的对比实验说明它们对系统性能的影响。

同样，如果想把自主探索改进写成算法贡献，就需要把“小圆初始化”“可达前沿选择”等方法形式化，并通过消融实验与原始 explore_lite 比较，而不能只描述一次调试过程。

## 我倾向采用的论文贡献

结合现有代码和工作量，我认为论文可以形成三个层次的贡献。

### 贡献一：5G LAN 边缘协同架构

建立车端感知与执行、5G LAN 通信、边缘侧 SLAM/Nav2/任务分配的多机器人巡检架构。

这一部分更偏系统贡献，需要通过网络延迟、带宽、边缘主机负载和多车扩展能力来验证，而不能只给出架构图。

### 贡献二：多机器人协同探索方法

在融合地图上统一提取前沿，综合信息增益、路径代价和机器人状态分配目标，并在任务失败或机器人离线时动态重分配。

这可以作为论文最主要的算法贡献。

### 贡献三：建图—导航—巡检一体化

将未知环境协同探索得到的地图转换为已有地图导航输入，再利用 AMCL、Nav2 和连续巡航完成重复巡检。

这部分体现两个工作空间的真正融合，也能说明研究并非只追求地图覆盖率，而是最终服务于桥梁巡检任务。

## 实验应该怎样围绕论文主线展开

实验不需要验证每一个工程功能，而要围绕论文提出的方法设计对比。

### 协同探索实验

可以比较：

1. 单机器人 explore_lite；
2. 多机器人各自独立探索并融合地图；
3. 加入统一前沿分配的多机器人协同探索；
4. 在方案 3 基础上加入冲突处理和动态重分配。

主要指标包括：

- 达到相同覆盖率所需时间；
- 重复探索面积；
- 总行驶距离与各机器人任务均衡程度；
- 前沿目标成功率；
- 机器人之间的最小距离和冲突次数；
- 地图融合误差。

### 5G LAN 与边缘计算实验

记录：

- LaserScan、融合里程计和 TF 的传输延迟与抖动；
- 一台、两台和四台机器人同时工作时的带宽；
- 边缘主机 CPU、内存和算法周期；
- 网络质量下降时的导航成功率；
- 机器人掉线后的任务重新分配时间；
- 失联情况下的安全停车和恢复时间。

### 重复巡检实验

使用融合后保存的地图，让机器人按照固定巡检路线持续往返。记录：

- 巡检点到达成功率；
- 重复到达同一位置的误差；
- 完成整条路线的时间；
- 动态障碍出现时的恢复能力；
- 多台机器人同时巡检时的任务完成效率。

如果后续加入病害检测，还可以增加病害位置在统一地图中的定位误差。当前两个工作空间尚未实现完整的病害识别，因此现阶段更适合把论文范围表述为“自主巡检与数据采集”，而不是直接声称已经完成病害检测。

## 论文结构可以怎样安排

按照这条主线，论文可以采用下面的结构：

1. 绪论：桥梁巡检、多机器人探索和边缘机器人研究现状；
2. 系统与问题定义：5G LAN、车端—边缘侧架构、坐标系和任务模型；
3. 单机器人建图与导航基础：SLAM、Nav2 和前沿探索基线；
4. 基于融合地图的多机器人协同探索方法；
5. 从协同建图到固定路线自主巡检的方法；
6. 单车、多车、网络和重复巡检实验；
7. 总结与展望。

第三章用于交代两个工作空间已有的基础能力，不需要写得比核心算法更长。第四章应该是全文重点，第五章负责把两个工作空间连成完整应用。

## 写在最后

这两个工作空间融合成论文的关键，不是把所有代码都写进正文，而是按照任务阶段重新组织：

> rslidar_slam_tk 负责在未知环境中获得地图，nav2_tk 负责在已有地图中执行巡检；论文的研究方法负责连接这两个阶段，并让多台机器人真正协同起来。

现有的 Launch、脚本、GUI、健康检查和速度仲裁保证系统能够稳定运行，它们是可靠的实验平台，但不是论文主线。论文真正需要突出的是协同任务分配、冲突处理、地图到巡检任务的转换，以及 5G LAN 边缘架构对多机器人协作的支撑。

只要始终围绕这条主线取舍内容，两个工作空间就不会变成两个项目的简单拼接，而会形成一篇目标明确、方法集中、实验闭环的论文。
